## Methodology notes

- Every item below was classified only after comparing the real, structured `actual`/`declared`/`historical` field values in file 1 for the fields relevant to its `section` (columns: type/nullability/default; constraints: type/reference/actions/definition; indexes: columns/method/uniqueness/predicate; enums: value AND ordinal position; extensions: exact version string). Name similarity/dissimilarity was never used by itself to conclude equivalence or difference.
- Where useful, additional read-only evidence was drawn from `prisma/schema.prisma`, files under `prisma/migrations/`, and scripts under `scripts/db/` in the repository. No database was queried live in this pass (no obviously-available safe read-only connection was used; see the "database access" note at the end).
- `NAME_TRUNCATION_EQUIVALENT` is applied to 50 items, all index/constraint identifier pairs proven byte-for-byte identical in every substantive field (columns, uniqueness, predicate, referenced table, FK actions) once the name itself is set aside. Two distinct identifier-divergence mechanisms were found and are documented per item: (a) classic PostgreSQL NAMEDATALEN 63-byte silent truncation of an over-length autogenerated identifier, applied differently by raw SQL (naive left-truncation) versus Prisma's schema-engine (base-segment truncation then fixed-suffix re-append) -- verified computationally for every such pair by reconstructing the shared full-length candidate name; and (b) a deliberately short, hand-picked identifier chosen in the object's original hand-authored migration file, which schema.prisma's `@@index`/`@@unique`/`@@relation` declaration never overrode via an explicit `map:`, so Prisma's own naming convention independently generated a different (often also truncated) name for the identical column set. Both mechanisms leave the underlying database object semantically identical; only the string differs.
- `COMPARISON_ARTIFACT` (25 items) required first-party, in-repo evidence that the representational split is by design, not neglect. Two whole-object designs account for most of these: (1) `_prisma_migrations`, Prisma's own internal migration-ledger table (11 items: the relation, its 8 columns, its PK constraint, and its PK index), which `schema.prisma` cannot and does not declare by Prisma's own tooling design; and (2) `localization_geometry_supersessions`, a table whose own creating migration (`prisma/migrations/20260823160000_add_localization_geometry_supersession/migration.sql`) states in its header comment, verbatim, that it is a "raw SQL access, not a Prisma model" projection table (12 items: the relation, its 6 columns, its 2 constraints, and its 3 indexes). A third, narrower case (`legal_corpus_chunks_record_id_chunk_index_chunk_version_key`) was classified `COMPARISON_ARTIFACT` because the identical object is already proven to match perfectly at the index level elsewhere in the full (non-held) comparison dataset, indicating the constraint-level miss is a gap in Phase B's constraint-extraction step rather than real drift. A fourth (`legal_corpus_chunks` HNSW index) is backed by a dedicated, dated, checked-in raw-SQL migration file plus an explicit schema.prisma comment documenting that pgvector/HNSW objects are deliberately managed outside the declarative schema. (11 + 12 + 1 + 1 = 25.)
- `TRUE_SCHEMA_DRIFT` (19 items) is used where a real, evidenced divergence exists and the fact of the divergence is not reasonably in doubt, even where full provenance (who/when) could not be established. This includes two orphaned undeclared columns on `Project`, a genuine missing `@map` and a genuine missing vector dimension in `schema.prisma` (both proven directly from the source file), two confirmed redundant/duplicate indexes on `attachments` (proven by the existence of a separately-matching, already-ratified modern index covering the same column), two ungoverned production-only indexes (one backed by a checked-in script, one with no trail at all), all 9 held enum-value ordinal-position mismatches (value sets agree everywhere; only Postgres-side ordering differs, and ACTUAL/HISTORICAL agree with each other against DECLARED alone), and the single pgvector extension version mismatch (0.8.6 actual vs 0.8.2 declared/historical).
- `OWNER_DECISION_REQUIRED` (4 items) is reserved for cases where a real difference exists but no evidence establishes which side should become canonical, either because the two forms are functionally equivalent Postgres defaults with no loss either way (`PostgisImportBatch.imported_at`/`started_at`, `legal_corpus_chunks.created_at` -- all three are `now()` vs `CURRENT_TIMESTAMP`, which schema.prisma's `@default(now())` is documented to compile to, but confirming this doesn't settle which literal form the frozen baseline should adopt or how the ungoverned `PostgisImportBatch` table should be governed going forward), or because a real definitional difference (a partial-index predicate) has no supporting migration/script evidence either way (`legal_corpus_chunks_chapter_paragraph_idx`).
- `UNRESOLVED` (0 items): every one of the 98 items could be resolved into one of the other four categories using file 1/file 2 plus repository evidence; none required guessing.
